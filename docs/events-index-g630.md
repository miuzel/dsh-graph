# 事件流增量索引（g-630）

`dsh-graph status` 在大看板上曾随事件流**线性变慢**（18404 事件实测 median 148ms，超 100ms 判据）。
g-630 为事件流引入**增量索引**，把「每次逐行全量扫描」换成「O(1) 字节探测 + 可证增量」。
本文记录设计、失效策略与**如实**的边界。

实现：`core/cli/events-index.ts`（索引与探测）、`core/cli/goal-files.ts`（目标文件枚举/读取的轻量叶子模块）。
测试：`core/tests/g630-events-index.test.ts`（22 用例，含 3 组真源码副本反向变异）。

## 1. 索引里到底存了什么

索引只存**事件流的派生物**，全部可由事件流纯函数推出：

| 字段 | 含义 |
| --- | --- |
| `eventCount` | 已确认的事件条数（= core `readEvents` 的 `length`） |
| `lastEvent` / `lastEventTs` | 末事件名与时间戳 |
| `size` / `ino` | 记录时的事件流字节数与 inode 标识（`dev:ino`；Windows 无 ino 时为空） |
| `headLen` / `headSha` | 头部**前 `headLen` 字节**的 sha256（`headLen = min(4096, 记录时 size)`） |
| `version` | 索引格式版本（当前 `1`） |

**不在索引里**：目标数、规则库版本、project.yaml 状态、文件探针 —— 它们各有自身真源，
不掺进事件索引（避免「一档缓存混装多种真相」）。

## 2. 一致性校验：只认「逐字节可证的增量」

每次 `status` 做一次 `open` + `fstat` + 读头部定长前缀 + 读尾部窗口（与事件体量无关），然后：

| 观测 | 判定 | 处置 |
| --- | --- | --- |
| `size` 变小 | 截断 | 回退全量校验 + 告警 |
| `dev`/`ino` 变化 | 被替换 | 回退全量校验 + 告警 |
| `size` 相等且 `headSha` 相同 | 未变 | 命中原值 |
| `size` 变大且 `headSha` 相同 | **纯追加** | 只解析新增区间的完整行 |
| `size` 变大但 `headSha` 不同 | 非纯追加（改写/替换） | 回退全量校验 + 告警 |
| 末行不可解析 / 追加区间无法逐行确证 | 可疑 | 回退全量校验 + 告警 |

### 为什么「头部指纹相同」就能认定纯追加

`appendEvent` 以 `O_APPEND` **单次**写入 `JSON.stringify(rec) + "\n"`，单条事件实测均 < 4KB，
且 `writeSync` 对普通文件**不截断到短写**（Node 文档明示）⇒ 一条事件要么整行写入、要么抛错。
因此**不存在**「先覆盖 4KB 前缀、再补尾部」的合法写入路径：头部被改写只能来自外部破坏，
此时 `headSha` 必变。

### `headLen` 为什么必须记进索引（实测踩到的坑）

最初实现每次都用 `min(4096, 当前 size)` 现算头部长度。小文件（< 4KB）的「头部前缀」就是整个文件，
**后续追加的字节会进入这个前缀** ⇒ 哈希覆盖的字节变多 ⇒ `headSha` 必然不同 ⇒ 正常追加被误判成
「非纯追加」，每次都退回全量校验（实测：追加检测用例直接变红）。记下 `headLen` 后，哈希恒覆盖
「记录时的那前 `headLen` 个字节」，语义才稳定。

## 3. 失效与回退策略（判据 3）

**任何不确定都不给数**：

| 情形 | 行为 | 用户可见 |
| --- | --- | --- |
| 索引不存在（首次使用） | 回退全量校验并写索引 | 无告警（正常冷启动） |
| 索引 JSON 损坏 | 回退全量校验 | `告警：事件索引已损坏（已退回全量校验）：…` |
| 索引结构非法（缺字段/自相矛盾/指向别的文件） | 回退全量校验 | `告警：事件索引结构非法（已退回全量校验）` |
| 索引版本不匹配 | 回退全量校验 | `告警：事件索引版本不匹配（已退回全量校验）：期望 v1，实际 42` |
| 事件流截断 | 回退全量校验 | `告警：事件流被截断（A → B 字节，已退回全量校验）` |
| 事件流被就地改写 | 回退全量校验 | `告警：事件流非纯追加变更（头部指纹变化，…）` |
| 事件流被替换（inode 变） | 回退全量校验 | `告警：事件流文件被替换（inode 变化，…）` |
| 事件流真损坏（core 也判红） | 报错并**非零退出** | `问题：事件流不可解析：events.jsonl 第 N 行…` |
| 缓存目录不可写 | 静默降级（只慢不坏） | 无告警、不影响结论 |

**告警 vs 问题的分工**：索引失效是**缓存层面**的事，回退本身已给出权威结论 ⇒ 记 `告警`，
**不**让 `status` 非零退出；而事件流本身损坏（`core.readEvents` 也失败）才记 `问题` 并退出 1
（g-314 判据 4 的既有语义不变）。

## 4. 索引放在哪里（判据 4）

```
默认： $XDG_CACHE_HOME/dsh-graph/events-index-v1-<root 路径 sha256 前 32 位>.json
覆盖： DSH_GRAPH_CACHE_HOME=<dir>        （隔离实例 / 测试用）
```

- **不进 `.dsh-graph/`**：那是事件流真源所在目录，写入会污染既有语义与格式（判据 4）。
- **不进源码树**：不产生未跟踪文件，不影响 `git status`。
- 文件名由 graph root 的 sha256 派生 ⇒ 多块看板互不干扰；索引**不含**任何看板内容（只有计数与哈希）。
- **纯缓存**：可随时删除。删掉只会退化为全量校验 —— 不会错，只会慢一次。

## 5. 目标文件枚举的同类优化（判据 1 的必要条件）

只砍事件流不够：`status` 还会急切加载 1.4 万行的 `core/ops.ts` 单体（实测冷启动 ≈69ms，
其中 `worktree.ts` ≈38ms、`yaml` ≈18ms），而 `status` 只需要「枚举目标文件 + 读 frontmatter +
读 project.yaml 的标志」。

处置：把 `listGoalFiles` / `loadGoal` / `findGoalFile` / `readRulesVersion` / `assertNoSymlinkPath`
的实现下沉到轻量叶子模块 `core/cli/goal-files.ts`（**唯一一份**），`ops.ts` 改为转调 + re-export
（语义与调用点不变，既有单测继续覆盖同一条代码路径）。`readProjectConfig` 语义仍以 ops 为真源，
改为**按需** `import`（因此 `collectStatus` 变为 `async`）。

## 6. 边界与未验证项（如实）

- **首次运行仍需全量校验**：索引不存在时 `status` 会全量扫一遍并写索引。一次冷启动、之后命中。
  缓存目录被清空（系统清理、切换 `DSH_GRAPH_CACHE_HOME`）后会再付一次。
- **Windows 无稳定 inode**：Node 在 Windows 上 `st.ino` 恒为 0 ⇒ 「被替换」改由 `size + headSha`
  判定。同名同长但**头部相同、中间被改**的替换在 Windows 上识别不到（Linux 上由 inode 拦住）。
  该场景需要外部工具「精确保持前 4KB 与总长、只改中间」才可能触发；本机为 WSL2，**未在原生
  Windows 上验证**。
- **< 4KB 的小事件流**：头部长度的取舍已由 `headLen` 修正；小看板本来就不慢，索引收益可忽略。
- **性能数字的环境依赖**：见第 7 节，均在同机同 Node 版本实测，机器负载会影响绝对值。

## 7. 实测前后对比

口径：`spawnSync(node, [entry, "status", "--root", <root>])` **全进程**耗时（含 Node 启动、
模块加载、执行与退出）；入口 `dist/bin/dsh-graph.mjs`（发布形态）；Node `v26.7.0`；
WSL2（Arch Linux）；基线 `node -e 0` ≈ 20ms。

数值见 `docs/dsh-graph-guide.md` 的「冷启动实测」一节（同一处维护，避免两处数字漂移）。
