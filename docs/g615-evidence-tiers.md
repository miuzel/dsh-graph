## 2. 判据 4 与判据 8：`UNVERIFIED` 的口径

### 2.1 判据 4 为什么是 `UNVERIFIED`

- 本轮环境**没有可用的模型路由**：隔离实例能起来、页面能打开，但**无法建立会话**（没有可派发的模型），
  因此**无法真实触发「子代理绑定失败补偿」**这条路径；
- 按负责人裁定与全局约定，**不得**改用外部 workspace、**不得**使用负责人凭据去接真实模型；
- 因此判据 4 **既不算通过、也不算缺陷** —— 代码路径没有被执行过，只被读过。

**本轮能做且已做的**：确认该路径的代码真实存在（不是凭空假设），见 §2.2。这**不构成**验证。

### 2.2 构造方案（未来可执行，本轮未执行）

目标是让「绑定失败补偿」在真实宿主上触发，并断言**宿主侧确实中断了已起的执行**：

1. **起隔离实例**：`bash scripts/dsh-test-web.sh <版本> --port 3082`，
   `DSH_HOME` 与 workspace 都在项目 `tmp/dsh-test/...` 内（绝不指向用户实例）；
2. **测试专用 provider**：在隔离实例的 `DSH_HOME` 配置里加一个只用于测试的 provider（本地假 endpoint，
   例如一个返回固定 401 的本地 HTTP 服务）。它只存在于隔离实例，不进用户配置、不带用户凭据；
3. **注入失败**：让子代理派发路径命中该 provider 并**返回 401**（或让绑定在 ready 前断开）；
4. **断言宿主侧终止**：在隔离实例的日志 / 事件流里断言
   「`binding` 失败后，已起的执行被真正 abort / 终止」，**不是**仅组件停止显示；
   同时断言隔离实例内**没有**残留运行中的执行（无 busy 子代理、无在飞请求）；
5. **取证**：保留隔离实例日志片段 + 执行 ID 的时间线（起 → 失败 → 终止），落 `tmp/`（不入库）。

**本轮未执行的原因**：第 2 步需要一个实际可路由的模型 endpoint，而按裁定不得引入外部服务/凭据。
需要负责人提供「允许使用的测试模型路由」或授权起一个本地假 endpoint 后才能执行。

### 2.3 判据 8 的现状

本轮**没有启动隔离实例**，因此「不修改用户实例与凭据、隔离实例 DSH_HOME/workspace 位于 `tmp/`」
**没有实际执行证据** ⇒ 记 `UNVERIFIED`，不声称成立。

**关于 `tmp/g615-e2e/isolated-no-model.png`（att-001 遗留）**：该文件**只是隔离实例的首页截图**
（实例起来、页面打开、无可派发模型），它**不能**作为判据 4 的证据，也不能作为「真实渲染」的证据。
此处**明确标注为无效证据**，引用它视为错用。`tmp/` 不入版本控制，该文件不随本变更交付。

## 3. M3：att-001 的结论为何被证伪，以及修复后钉住的是什么

### 3.1 被证伪的陈述

att-001 的 M3 只跑了 `expectAbaRecutClean`（A→B→A 回切），在那个场景下「只删 token 守卫」的变异体**保持 GREEN**，
于是结论写成「token 守卫无判别力、三重冗余」。这是**判宽**：单一场景不足以推出整条守卫无判别力。

### 3.2 实测：直切场景会泄漏

在**同一组件实例**上，A 已加载后**直切** B（不是回切）：

- 生产 bundle：首帧渲染 `读取中…`；
- 只删 token 守卫的变异体：首帧渲染 `🤖 MSG_A` —— 旧身份数据直接暴露。

原因：直切时新身份的读取**尚未回包**，此时唯一能挡住旧数据的就是「状态里存 token，比对不通过就回退 loading」
这道守卫。ABA 回切之所以看不出差异，是因为回切到 A 时 A 的请求尚未回包、画面本来就在「读取中…」，
B 的迟到响应若抵达也落在 loading 之上（att-004 实测：双删变异体在 ABA 场景会显示 `MSG_B`，
但只删 token 的变异体保持绿 —— 说明 ABA 场景的「绿」来自**尚处 loading**，与 token 守卫无关）。

### 3.3 修复后 M3 钉住的是

- **主判据**：`mutation: "token-guard"` 的变异体下，`expectIdentitySwitchFirstFrameClean`（直切首帧）
  **必须变红**，且失败信息指向「首帧不得显示上一身份数据」；
- **第二条对照（保留并写明）**：**ABA 回切不泄漏 ≠ token 守卫无判别力** —— 同一变异体在 `expectAbaRecutClean`
  下保持绿，这记录的是「ABA 场景下画面尚处 loading、看不出 token 缺失」这一事实，
  **不是**判别力缺失的证据；
- **正向**：生产 bundle 两种场景都为绿。

### 3.4 修复前后对照（实际输出）

修复前（att-001 的 M3，只测 ABA）：

```text
✔ g-615 M3（如实标注：不构成判别证据）：只删 token 比对的变异体仍被挡住
```

修复后（att-002 的 M3，A 已加载 → 直切 B）：

```text
✔ g-615 M3：只删 token 守卫 + A 已加载 → 直切 B，首帧泄漏旧数据 ⇒ 断言必红
```

同一变异体在两种场景下的实测差分（`tmp/g615/probe-m3.ts`，一次性探针，不入库）：

```text
PROD   : {"loaded":"🤖 MSG_A","first":"读取中…"}
MUTANT : {"loaded":"🤖 MSG_A","first":"🤖 MSG_A"}      ← 直切首帧泄漏
PROD   expectIdentitySwitchFirstFrameClean => GREEN
MUTANT expectIdentitySwitchFirstFrameClean => RED: 切换身份首帧不得显示上一身份数据（实得 🤖 MSG_A）
PROD   expectAbaRecutClean => GREEN
MUTANT expectAbaRecutClean => GREEN                     ← 回切时画面尚处 loading，看不出 token 缺失
```

att-004 补测（ABA 场景下四态对照，说明「ABA 的绿」不归因于任一守卫）：

```text
[ABA] A 已加载 → 切 B（未回包）→ 回切 A → B 迟到
PROD    : 回切首帧 读取中… / B 迟到后 读取中… / 最终 🤖 MSG_A
NO_ALIVE: 同上（恒为 读取中…）
NO_TOKEN: 同上（恒为 读取中…）
双删    : B 迟到后 显示 🤖 MSG_B            ← 只有两道守卫同时缺失才看得出
```

注：修复前的 M3 **在测试报告里是一行 GREEN** —— 它当时断言的是「变异体仍正确」，因此「GREEN」
恰恰是这个判窄版本的产物，不能读成「token 守卫无判别力已被证明」。

## 5. att-003 / att-004 返工：评审 BLOCK 的缺陷与修复（实际输出）

本节只记录**已实测**的结论；未实测的一律不写。

### 5.1 迟到响应注入：att-003 的「已打通」不成立，att-004 改为真迟到语义

两段历史缺陷需要分清：

1. **att-002 的缺陷（机制层）**：假宿主在 `abort` 时 `reject(...)`，而 `answerLate` 随后才 `resolve(...)` ——
   对已 settled 的 Promise，`resolve` 是 **no-op**（ES 规范），迟到的旧响应从未抵达组件。
   att-003 把 abort 改为**只置 `aborted` 标记、不 reject**，这一步是对的。
2. **att-003 自己的缺陷（时序层，att-004 发现）**：att-003 的 `expectLateResponseIgnored` 先
   `answer("A")` 让 A 回包成功，再 `answerLate("A")` 对**同一个已 settled 的 Promise** 二次 resolve
   ⇒ 仍是 no-op。于是 att-003 声称的「迟到注入已打通」在它自己的用例里并不成立。

att-004 的口径（唯一）：**A 在切换身份时还从未回包**，直切 B、B 先回包建立可被污染的基线，
**然后** A 才第一次回包。此时 A 的 `await` 才真正返回到达组件。

四态实测（att-004 独立探针，`tmp/` 一次性脚本，3 次重复一致）：

| 时序 | PROD | NO_ALIVE | NO_TOKEN | NO_ALIVE+TOKEN |
| --- | --- | --- | --- | --- |
| A 已回包→切 B→**再次** resolve A（att-003 的伪迟到） | 读取中… | 读取中… | 读取中… | 读取中… |
| A 未回包→切 B→B 回包→**A 首次回包**（真迟到） | 🤖 MSG_B | 读取中… | 🤖 MSG_B | **🤖 MSG_A** |

读法（如实，不包装）：

- **真正挡迟到写入的是渲染期 token 守卫**（`storedState.token === token`）：只删 alive 时，迟到数据
  **确实写进了 `storedState`**（可观测痕迹：画面从 `MSG_B` 退化为「读取中…」，正是 token 守卫否掉脏 state 后回退 loading），
  但**不会渲染成 `MSG_A`**。alive 只阻止「写入 state」这一步，画面层不可观测。
- **单删 token 不泄漏**：alive 在 cleanup 里已置 false，迟到写入被拦在 `setState` 之前，画面保持 `MSG_B`。
- ⇒ 判据 3 的泄漏路径需 **alive + token 同时缺失**才可观测，**单机制不可分离**。反向证据因此只能由
  M2（双删）承担，不再声称任何单一机制提供判别力。

**被删除的论证（att-003 曾写）**：「只删 alive 时迟到数据会在同一身份重挂载后复活为 🤖 MSG_A」——
**已证伪**：① 实测 NO_ALIVE 画面恒为「读取中…」；② `RecentRecords` 的 token 来自
`React.useMemo(() => ({}), [parentId, childId, mode])`，同一 props 再提交帧时实例复用
（实测 `sameInstance: true`，label 前后均为 `RecentRecords #1`），**没有重挂载路径**。

**M9 的处理**：`dropAliveKeepAbort` 旧实现内部又调了 `dropTokenGuard`（实为双删，名不副实）。
att-004 改为**真的只删 alive**（并断言变异体仍含 token 守卫与 abort），M9 **降级为正向说明性用例**——
它断言「只删 alive 时画面仍不出现 `MSG_A`」，并断言可观测痕迹（退化出 `MSG_B`），**不**声称「必红」。
自检：若把 M9 的变异体换成双删，该用例实测变红（`实际 🤖 MSG_A`）⇒ 说明它的「不泄漏」断言有判别力。

注：`dirtyCount()` **不能**当作「响应抵达」的证据 —— 组件切换时退订会把仍挂着的实例标脏，
实测四态在注入前后都是 1。判别力只认画面差分。

### 5.2 判据 3 的分档理由（更正）

att-002 写明「M2（删 alive+abort 必红）」，但旧版因 aborted 立即 reject，M2 的红**只**来自
「身份切换必须 abort 旧身份在飞请求」这一条 —— alive 从未被触及。att-003 试图把 alive 的判别力
记到 M9 名下，但 M9 实为双删且其「重挂载复活」论证被证伪。att-004 更正为：

- M2（删除 alive + token）在**真迟到**注入下实测变红且泄漏 `MSG_A` ⇒ 它是判据 3「不得写入」唯一可归属的反向证据；
- 单机制（只删 alive / 只删 token）均不泄漏 ⇒ 判据 3 的泄漏路径**需双删才可观测**，该结论本身就是对
  产品行为如实描述（两道守卫在「迟到写入不得覆盖看板」这一目标上冗余，token 守卫是提供可观测量的一方）；
- 因此本页不再把任何单一机制标注为判据 3 的判别者。

### 5.3 缺陷 2：判据 2 的 mode 维度曾是同义反复

`subagentMode` 只被 `SessionPanel` 消费，att-002 却把 mode 断言挂在 `RecentRecords` 上 ⇒
standard ≡ minimal 恒绿。现将 `expectModeSwitchNoStaleNoEmpty` 改挂 `SessionPanel`，并要求两模式
各自渲染出自己的模式值；M12（抹掉 `${props.subagentMode}`）实测变红。

### 5.4 缺陷 3：跳过前置曾掩盖判别力

构造「永远 loading、A 永不可见」的变异体（删掉唯一的 `loadHistory()` 调用）：旧写法带
`mutation: "token-guard"` 时为 **GREEN**（前置被跳过，泄漏断言反而白送）。现在跳过前置时由
