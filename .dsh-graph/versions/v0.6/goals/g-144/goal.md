## 目标描述


v0.6 以“版本泳道生命周期与可维护性”为主线：补齐版本创建/维护/发布的闭环，并先降低后续 UI 迭代的 client 维护成本。

**推荐核心范围（待负责人确认后才排期）**

1. **g-142：client.js 重构**——先按职责拆分浏览器看板代码，保持既有行为与 API；这是后续新增版本操作 UI 的维护性前置。
2. **g-134：版本泳道管理**——支持创建、重命名、删除空版本泳道，覆盖版本元数据与看板操作入口。
3. **g-135：版本泳道发布**——在负责人发布 gate 下，将版本标记 released；发布前强校验没有非 delivered 的版本目标，并记 `version.released` 事件。

**可选并入项（请负责人决定）**

4. **g-143：跨会话认领 planning / collecting / ready 目标**——改善多会话协作，可在 g-142 完成后与 g-134/g-135 并行；若希望 v0.6 保持小而聚焦，则留待 v0.7。

**明确暂缓**

- g-128（上下文卡片管理）、g-138（目标暂缓）、g-139（目标合并）：按此前“后续版本再安排”的决定，本轮不自动回迁。
- g-132/g-133（配置管理）、g-136（项目级子代理规则）、g-103/g-104/g-105：范围较宽或需先消除重叠，留待后续独立规划。

**建议顺序与发布条件**

- 阶段 A：g-142 重构并完成行为回归验证；
- 阶段 B：g-134 版本泳道管理；
- 阶段 C：g-135 发布 guard 与端到端验证；
- 阶段 D（若纳入）：g-143 跨会话认领；
- 发布前：全部范围目标 delivered、代码已提交、全量测试通过、负责人完成 review 与发布决策。

v0.5 已按负责人指示记录 released：npm `dsh-graph@0.5.1` 已发布；g-111 继续跟踪 awesome-dsh-plugin PR #2773 的合并，不阻断 v0.6 规划。
