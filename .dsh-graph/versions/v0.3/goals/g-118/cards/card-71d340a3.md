# g-118 调研报告：DSH 插件内容自动注入会话机制

**调研范围**：DSH 安装目录（`.../node_modules/@deepseek-ai/dsh/`）源码阅读 + dsh-graph 项目现状。纯只读，未修改任何文件，未做实机验证。

## Q1. `dsh-agent-instructions` 的注入机制

**结论：它是 Cordis 插件（apply(ctx, config)，非 Service），自动装载工作区内的 AGENTS.md/CLAUDE.md 文件，作用域是"工作区（cwd/项目根）"而非 session.id，且没有按会话/agent 条件注入的能力。不可直接用于按会话注入主管守则。**

关键证据（`dsh-agent-instructions/lib/index.js`，1311 行）：
- **发现协议**：user-global `$DSH_HOME/AGENTS.md` + 从项目根（`.git` 等 marker）到 cwd 每层目录的 `AGENTS.md`/`CLAUDE.md`（含 `.local` 变体）：L15-17 `DEFAULT_INSTRUCTION_FILE_CANDIDATES`；L473-481 `findProjectRoot`；L545-573 `discoverInstructionFiles`。
- **渲染**：文件内容包装进 `<system-reminder>` 帧的 user 角色消息：L110-115（帧常量）、L255-265 `buildInstructionText`、L755-767 `workspaceContextHook` → `createUserMessage`（source.kind=`agent-instructions`）、L773-784 `workspaceContextMessage`。
- **注入时机**：`ctx.on("agent/pre-step", ...)`（L1271-1288）每步前把渲染结果同步进 `agent.inbox`（`composeAndSync`/`syncInbox`，L1198-1222）；`tools/result`（L1289-1308）监听 read/write/edit 触碰文件后增量刷新。
- **谁消费**：`dsh-agent-loop` 的 `preStep()` 组装消息 → `agent/pre-step` waterfall 把 user 消息并入当步输入（`dsh-agent-loop/lib/index.js` L492-514）。
- **粒度控制**：只有 `cwd`/项目根/`dshHome` 可配；同一 workspace 的所有会话（含执行子代理，其 cwd 继承父会话）一视同仁。无任何 session.id 判定点。`ctx.get("fs")` 缺失时整个插件 no-op（L1101-1102）。
- **默认启用**：`$DSH/config/agent-presets/standard/agent.cordis.yml` 内有 `- id: agent-instructions / name: '@deepseek-ai/dsh-agent-instructions' / config: { maxBytes: 65536 }`（standard preset 的 agent-plane 行）。

> 对本目标的意义：它是"工作区文件自动装载"，不是"插件自定义内容注入"。若把主管守则放进 AGENTS.md，所有在该 workspace 的会话（含执行子代理）都会收到——违反隔离约束，否决此路径。

## Q2. skill 的自动触发/注入机制

**结论：目录摘要自动注入、正文按需加载。`whenToUse` 只是元数据，没有任何自动匹配/自动装载逻辑。不存在"新会话不调用 skill 也能看到正文"的现成机制。**

关键证据：
- **加载协议**（`dsh-skill-filesystem/lib/index.js`）：FileSystemSkillProvider 扫描根（L150-188）：项目 `.dsh/skills`、`.agents/skills`（L154-164），用户 `$DSH_HOME/skills`、`~/.agents/skills`（L171-180），`customSkillDirs`、`DSH_BUNDLED_SKILL_DIR`（L181-186）。skill 形态 = 目录 `SKILL.md` 或平铺 `*.md`（L586-592）；YAML frontmatter 必需 `name`/`description`，可选 `whenToUse`、`invocation`（L664-699、L845-846）。
- **注册表服务**（`dsh-skill/lib/index.js`）：Service `"skills"`；`registerProvider(create)`（L147-183）、`register(skill)` 运行时注册（L193-215，默认 `invocation:{modelInvocable:true,userInvocable:true}`）、`list/snapshot/get`（L224-264）。分层：`ScopedLayers`。
- **目录注入**（`dsh-tool-skill/lib/index.js`）：`agent/pre-step` 时把 `<available_skills>` 目录作为 user 消息发布（L181-214、`renderCatalogMessage` L216-239），仅当 `ctx.tools.get(skillTool.name, agent) === skillTool`（该 agent 可见）时才发布（L185-192）。
- **正文注入仅两条路径**：①模型调用 `skill` 工具（execute L116-135 → `ctx.skills.get` → 返回 content，render 为 `<skill_content>`）②用户消息 `/name` 手势直接注入（L146-180，source.kind=`skill-invocation`）。
- **`whenToUse` 的消费方**只有展示/API（`dsh-host-apiproxy`、`dsh-client-connection`、`dsh-tool-workflow`），无自动触发。
- **dsh-graph-host 现状**（`dsh-graph-host/index.js` L628-632）：`ctx.get('skills').register({name:'dsh-graph-supervisor', content: GUIDE})` 与 `dsh-graph` 使用指引都在 `apply()` 期全局注册 → 全局层 → 所有 agent（含执行子代理）的目录都可见、都能调 `skill` 工具加载主管守则正文。这就是"按需调用、不保证注入、且执行子代理也能拿到"的现状根因。

## Q3. 插件向会话注入 instructions 的正规路径

**结论：`systemPrompt` 服务是正规注入点（system 提示词段落 / runtime context），支持 `text` 为函数按组装上下文动态渲染；作用域由 ScopedLayers 控制（全局 vs per-agent）。另有 `agent/pre-step` 消息注入、`agent/created` 钩子、agent preset 三条辅助路径。**

关键证据：
- **`ctx.systemPrompt.section({name, order, text})`**（`dsh-system-prompt/lib/index.js` L186-189）：注册 system 提示词段落。`text` 可以是 `(context) => string`（L271）。空文本段落被丢弃（`renderPrompt` L66 filter）。
- **组装上下文携带 agent**：`assembleContextFor(agent, signal)` 返回 `{agent, scope, signal}`（`dsh-agent/lib/index.js` L384-390）；`dsh-agent-loop` 每步调用 `systemPrompt.assemble(assembleContextFor(this, signal))`（L497）。`ReactLoopAgent` 有 `id`/`session`/`ctx` → `context.agent.session.id` 可拿。
- **`ctx.systemPrompt.context({name, order, text})`**（L196-199）：动态运行时上下文，渲染成 user 角色 "Current runtime context" 消息，经 `RuntimeContextProjection`（`dsh-agent-loop/lib/index.js` L26-95）在内容变化时落会话。
- **作用域机制**：`ScopedLayers.effect` 用 `scopeOf(ctx)`（调用方 ctx）决定注册层（`dsh-scope/lib/index.js` L189-217）；`scopeChainOf` 最近层优先（L276-280）。`dsh-system-prompt` 错误信息明确："for a per-agent override, register through that agent's `agent.ctx`"（L142-144）。
- **per-agent 钩子**：`ctx.on("agent/created", ({agent}) => ...)` 全局插件可拿到 live agent（`dsh-agent/lib/index.js` L660-681）；`dsh-agent-presets` 自己就用此模式做预设校验（L863-867）。
- **persona 槽**：`dsh-persona`（44 行）在调用 ctx 的 scope 注册 `deployment:persona` section（`PERSONA_ORDER=0`），preset 内挂载即按会话 shadow 全局 persona——证明"插件经 scoped ctx 注册 prompt 段"是成熟路径。
- **agent preset**（`dsh-agent-presets/lib/index.js`）：每个会话从 `agent.cordis.yml` 组成 model-facing 插件集（L770-791、`resolveSessionPreset` L762-768）；`config/agent-presets/{standard,minimal,cordis,code}` 为出厂预设。

## Q4. 会话作用域隔离的可行性

**结论：完全可行。能拿到 session.id 并与 project.yaml 的 `supervisor.session` 比较（`readSupervisorSession` 已存在并被 boardPayload 使用）；DSH 没有"按 session.id 过滤 instructions"的现成机制，但两条等价的实现路都能达成约束，且必须避开一个陷阱：preset 级/全局级注册会泄漏给执行子代理。**

- **陷阱（关键）**：子代理创建时加入父会话的 preset scope 链——`applyChildComposition`（`dsh-subagent/lib/index.js` L570-583）：`childCtx.get("agentPresets")?.composeFrom(childCtx, parent.ctx)`。因此 preset 级 section/skill 对父会话与其派生的所有子代理同时可见；全局级（dsh-graph-host 现状）更是对一切会话可见。**executor 子代理的 session.id 是独立的**（`childSessionMeta` L530-540 → `agents.create` 铸新 session id），所以以 session.id 做判定恒不命中。
- **可行路 ① 全局注册 + 条件渲染**：section/context 的 `text` 函数里判 `c?.agent?.session?.id === supervisorId ? GUIDE : ""`，非主管会话渲染为空 → 被丢弃（`dsh-system-prompt/lib/index.js` L66、L102）。隔离由值判定保证。
- **可行路 ② per-agent 层注册**：`agent/created` 监听器内经 `agent.ctx` 注册 section/skill → 注册进该 agent 的 scope 层；子代理 scope 链 `[child, preset, global]` 不含父 agent 层 → 天然不可见（连目录都不出现）。
- **project.yaml 键**：`.dsh-graph/project.yaml` 的 `supervisor.session: session-5f6bf96d-...`（带注释"换会话时更新"）；core 已有 `readSupervisorSession`（dsh-graph-host/index.js L366 使用）。
- **边界情况（claim 时序）**：新主管会话首轮时 project.yaml 可能仍指向旧会话 id → 首轮不注入；`graph_claim_supervisor` 落库后下一 step 的组装立即生效（per-step 组装）。建议流程上"先更新 supervisor.session 再开新会话"，claim 幂等兜底。

## Q5. 候选方案对比

| 方案 | 改动点 | 作用域控制 | 风险 | 推荐度 |
|---|---|---|---|---|
| **A. systemPrompt section + 条件 text 函数**（推荐） | `dsh-graph-host/index.js` `apply()` 内 `ctx.get?.('systemPrompt')?.section({name, order, text: c => c?.agent?.session?.id === readSupervisorSession(root) ? GUIDE : ''})` | session.id 精确匹配；子代理 id 不同 → 空 → 丢弃，不注入 | ①新会话首轮若 project.yaml 仍指旧 id 不注入（claim 后次 step 生效）②每步组装读文件（可缓存）③指南 14KB 进 system prompt 的 token 成本 | ★★★★★ |
| **B. agent/created 内经 `agent.ctx` 做 per-agent 注册** | `apply()` 加 `ctx.on("agent/created", ({agent}) => { if (id 命中) agent.ctx.get('systemPrompt')?.section({...}); agent.ctx.get('skills')?.register({...}) })` | per-agent scope 层；子代理链不含父 agent 层 → 天然隔离（连目录都看不到 supervisor skill） | 依赖 agent/created 时序与 agent.ctx 服务解析（需实机验证）；同样有 claim 首轮边界 | ★★★★（A 不干净时上） |
| **C. agent/pre-step 消息注入**（仿 skill catalog） | `apply()` 加 pre-step 监听，命中 session.id 注入 `<system-reminder>` user 消息；自带去重 | 同 A 的 session.id 判定 | 消息进会话历史、每步查重比较、实现复杂、可被 compaction 影响 | ★★★ |
| **D. AGENTS.md 或 preset 独占注入**（否决） | 把指南放 AGENTS.md / 专用 preset | 无——子代理继承 workspace/preset scope，必泄漏 | 违反"执行子代理绝不被注入" | ✗ |

**推荐：方案 A**。单一注册点、零新文件、不动 DSH 安装目录；隔离靠 session.id 值判定（executor 子代理 session.id 不同 → 空文本被丢弃），与"绝不注入执行子代理"的约束完全兼容。

GUIDE : '' })`（root 用 apply 期解析值；`readSupervisorSession` 现读 project.yaml，可带轻量缓存/容错）。
2. 建议把 GUIDE 包进 `<system-reminder>` 帧再注入（对齐 DSH instructions 外观约定，见 dsh-agent-instructions L110-115）；order 放 persona 之后。
3. 实机验收（后续阶段）：主管会话 system 提示词含指南；新开普通会话与 `graph_start_attempt` 派发的执行子代理 system 提示词不含指南；claim 后指南出现。
4. 可选加固（目录级隔离）：把 `dsh-graph-supervisor` skill 的注册从 apply() 挪到方案 B 的 `agent/created` 条件注册，使执行子代理的 `<available_skills>` 目录里也不出现主管 skill。
